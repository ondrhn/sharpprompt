# Where the wait goes

From Enter to a rewrite in the box a rough prompt waits for two model calls, and until now nothing on screen said so. This report covers what could be done without loading the plugin or calling a model; the measurements that need a live session (1a, 1c, the replies' lengths) come later, and their place is marked.

Data: the plugin's store on the author's machine, 9 October 2026, Claude Code 2.1.295 and 2.1.296. 15 classifications, 18 rough prompts, all rewritten, none timed out.

## What the store already says

| step | n | p50 | range |
|---|---|---|---|
| classify (Haiku) | 15 | 764 ms | 656 to 2,454 ms |
| rewrite, fork | 7 | 3,178 ms | 2,809 to 4,405 ms |
| rewrite, fallback completion | 11 | 2,490 ms | 2,054 to 4,742 ms |

So the usual wait is about 3 to 4 seconds, and the slowest classify and slowest rewrite together would make it 7. The longest rewrite came 258 ms short of the 5 second limit.

## 1b. The fallback completion's output tokens

The fallback completion (used before the conversation has a first reply) reported 370 to 889 output tokens for rewrites of 32 to 47 words, about 45 to 65 tokens of text, with no questions. The forks reported 130 to 313 for 40 to 55 words.

The completion is already called with `effort: 'low'`. The text it returns is the rewrite and nothing else as far as the cleaned result shows, so the rest is most likely thinking: Haiku 5.5 thinks by default and the engine's `ModelCompleteRequest` has no switch to turn thinking off, only `effort`, which is at its lowest. `ModelForkRequest` takes the prompt alone, so the fork has no lever at all. If it is thinking, there is nothing to change on either path.

To settle it, rewrite records now keep `replyChars`, the length of the reply before cleaning. A reply of ~250 characters with 500 output tokens is thinking; a reply of ~2,000 characters is text the cleaning threw away. This needs new rewrites, so it is filled in after the token overhead measurement ends (10 October, 22:40).

## 1a, 1c. Pending

Whether the prompt box stays usable during the wait, whether the engine shows its own spinner, and whether Esc ends the wait need a live session, and so does splitting a wait into classify, rewrite, fill and the extra timer tick (the usage log now records `fillMs`). Both wait until the token overhead window has ended: the plugin's store is shared between every copy of it on a machine, the one under development included, so loading the development copy writes into the store being measured.

One note from the attempt to start: a development session opened at 23:03 showed the main copy's last rewrite in `/sharp status`, which is how the shared store came to light. No prompt was sent. The store file's modification time moved from 23:03:56 to 23:05:25 with its size unchanged (17,385 bytes); the author's own session was running at the time.

## 2. A status line while the prompt is held

Done. `sharpprompt: checking` while the classifier runs, `sharpprompt: rewriting` while the rewrite runs, and the line goes when `decide` returns, whatever happened (clear, rough, keep, timeout, an error, a throw). Prompts the gate lets through, and every prompt with the plugin off, never show it. Six tests in `tests/submit.test.ts` check the order of the calls and that the line is cleared on each path.

The line does not say "Esc sends it as typed": whether Esc works during the wait is 1a, not yet measured.

## 3. The time limit

Kept at 5 seconds. 0 of 18 rewrites timed out, and the fork's time did not grow with the conversation: 3,137 ms with 108,012 tokens read from the cache, 4,208 ms with 53,012. A longer limit for long conversations would need a timeout rate over 10% there, and there is no timeout at all yet. A fork that loses the race cannot be stopped: `$.model.fork` takes no abort signal and ends only with the turn that started it, so it finishes and is billed (counted as late forks).

## 4. Skipping the classifier for plainly clear prompts

Not added. 300 typed prompts drawn from the author's own transcripts (929 typed prompts, 762 of them past the gate, mostly Turkish, median 20.5 words; the corpus is kept outside the repository) were run through six candidate rules:

| rule | prompts it would let skip the classifier |
|---|---|
| a file path with a line number (`calc.py:12`) | 0 |
| a code block | 0 |
| two or more numbered steps | 2 |
| 60 words or more and no question mark | 30 |
| a file path and at least 12 words | 4 |
| a pasted error or stack trace | 1 |
| any of them | 34 (11.3%) |

Even if Haiku called every one of those 34 clear, skipping them would save 11.3% of classifier calls, under the 15% the change had to clear. So the labelling run was not needed for the decision. The rules and the labelling are in `scripts/clear_rules.mjs` (`cover`, `label`, `eval`) for a corpus where they might matter.

## 5. The completion's output tokens

Waits for the `replyChars` numbers in 1b. If it is thinking, there is no setting left to change; if it is text, the instruction gets a "the rewrite only, nothing before or after it" line and the same ten prompts are measured before and after.
