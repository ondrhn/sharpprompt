# Benchmark v2, Fable 5.1: same picture as Sonnet

On the v2 corpus the rewritten arm passed 25 of 30 checks and the prompt as typed passed 12 (p = 0.0002). The gain is again in hidden-spec and remote-ref; on session state both arms passed everything. The numbers are close to the [Sonnet 5.5 v2 run](bench-2026-10-09-v2-sonnet-5-5.md) (13 and 25), so read that report for the corpus and the method.

Run on 9 October 2026 with Claude Code 2.1.295, model `claude-fable-5-1`, one repeat. Raw data: [runs/2026-10-09-v2-claude-fable-5-1.jsonl](../bench/runs/2026-10-09-v2-claude-fable-5-1.jsonl), its manifest and the judge's verdicts. Rewrites: [rewrites/fable-v2](../bench/rewrites/fable-v2), helper Haiku, oracle Sonnet 5.5; none came back KEEP, so all 30 cases are paired.

## Remote reference: raw changed both

| arm | check passed | target right | decoy untouched |
|---|---|---|---|
| raw | 1 | 10 | 1 |
| rewritten | 10 | 10 | 10 |

The raw arm failed 9 of 10 remote-ref cases, and in all 9 it changed the target correctly and the decoy too. As on Sonnet, it never picked the wrong function alone. The one raw pass is ref-boundary-over-budget. The rewritten arm changed the target only in all 10.

## Hidden spec: what raw guessed, what it asked

Fable's raw arm stopped and asked in one case only, spec-column-order ("I can't make this change yet because nothing in the repo or our conversation says what column order finance's import expects"). Sonnet stopped in three. In the other nine Fable guessed, usually said it was a guess, and built more around it (median 16 turns against Sonnet's 4.5 on this family):

- spec-csv-separator: fixed CSV quoting (a `1,000.00` amount split the row) and called it done; the user meant semicolons.
- spec-near-75: wired `alerts()` to `near_budget` at its existing 90%; the user meant 75%.
- spec-date-format: wrote MM/DD/YYYY behind a `FINANCE_DATE_FORMAT` constant and asked to confirm; the user meant DD.MM.YYYY.
- spec-refunds: parsed every negative format and added a refunds figure, but netted refunds into the category total.
- spec-top3-other: top 5 plus Other; the user meant top 3.
- spec-round-005: rounded to whole cents; the user meant 0.05.
- spec-eur-suffix: USD, "One assumption to check"; the user meant EUR.
- spec-hide-small: folded categories under 5% of the total into "other", which also folded Food; the user meant under 10.00.
- spec-sort-amount: largest first, right.

## Where the rewrite lost

The rewritten arm failed 5 hidden-spec cases:

- spec-csv-separator: the rewrite asked whether the import fails or needs a different layout, and where the format is written down. The oracle said "different layout" and "I don't know". Nothing about the separator; the model fixed the quoting and said it could not change the layout.
- spec-column-order: the rewrite asked nothing. The model stopped and asked, as the raw arm did.
- spec-top3-other: asked which categories to keep ("Largest only"). The model kept 3, by luck, but left out the Other line, which the user wanted and nobody asked about.
- spec-eur-suffix: asked where the currency should show and whether as ISO code or symbol. Not which currency. The model picked USD.
- spec-refunds: asked what a negative amount should become; the oracle said refunds, kept out of category totals and tracked separately. The model took them out of the overall total too; the user wanted that one net. The oracle's answer was right and incomplete.

In 4 of the 5 the rewrite did ask, but not the question the case turned on. Same pattern as on Sonnet.

## near-75

Here the rewritten arm passed. The model set `near_budget` to `>=` 75% ("returns true once spending reaches 75% of the limit"), so 75 of 100 warns. On Sonnet the same number went in with a strict `>` and failed.

This pass is partly an oracle leak. The rewrite's first question was "Which budget warning should fire earlier? Token budget / Spend budget", and the oracle answered "I only know that near_budget should warn from 75% of the limit". That names the function and the boundary the user never said. On Sonnet the oracle answered the same kind of question with "I haven't specified which one". So on this case Fable's rewritten arm got more than a real user would likely have given.

## Blind judge

Sonnet 5.5 as judge, same setup as the Sonnet run: request, context, `expect` sentence, two final answers in random order, arms hidden, final messages only.

- Pairwise: rewritten 22, raw 4, tie 4; sign test p = 0.0005 (ties left out).
- Score from 1 to 5: raw mean 2.90, rewritten mean 3.93, mean paired difference +1.03 (n=30).
- The judge's two answers agree in direction in 19 cases, disagree in 2, and are neutral in 9.

On session-state, where both arms pass, the judge split 3 / 3 / 4. On Sonnet it went 8 to 2 for the rewritten arm there.

## Method

Same runner, corpus and oracle as the [Sonnet 5.5 v2 run](bench-2026-10-09-v2-sonnet-5-5.md#method), with the rewrites made for the Fable rule family.

The run was cut in two by the account's usage limit. The first pass (09:52 to 10:18 UTC) finished 23 arms: every hidden-spec arm, both arms of ref-quote-report-csv and the raw arm of ref-quote-category-csv. The other 37 came back empty, 36 of them with "You've hit your session limit". We deleted those 37 lines from the run file and its manifest and started the runner again after the limit reset; it skips what the manifest already holds and ran the 37 (to 11:30 UTC). Both passes ran on Claude Code 2.1.295. One case, session-near, was run once more as a probe between the passes; that run was deleted and is not in the data.

The leak audit added after the run (`bench.mjs audit`, see the [Sonnet report](bench-2026-10-09-v2-sonnet-5-5.md#method)) flags 3 cases in these rewrites: spec-near-75 (`75`, `near_budget`), a real leak as described above, and spec-date-format and spec-round-005, which answer the question asked with a value not among the options and are not leaks. These rewrites were made before the oracle's no-naming rule.

Cost as the API would bill it (Max plan): 33.87 USD for the measured turns and 9.90 USD for the context turns, 43.76 USD in all; 2,292 seconds of run time. The rewrites, the oracle and the judge are not included.

## Limits

The limits of the Sonnet v2 run apply here too: we wrote the corpus to have something missing, one repeat, a model as oracle, the fallback rewrite template, a judge that reads final messages only, and the account's `~/.claude/CLAUDE.md` in both arms. On top of that, the oracle leaked on near-75, and the hidden-spec arms ran before the usage limit and the rest after it.

- The rewrites and their questions were written by the helper model, Haiku. In the plugin the rewrite is a fork of the session model (`$.model.fork`); Haiku writes it only as the fallback when there is no conversation to fork yet. So the questions measured here come from a different model than the plugin's usual ones.
